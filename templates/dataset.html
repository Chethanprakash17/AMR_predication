Dataset: MIMIC-IV ICU Clinical Database

This project utilizes the MIMIC-IV (Medical Information Mart for Intensive Care IV) database, a freely accessible critical care database developed by the MIT Lab for Computational Physiology.

Dataset Overview

Attribute Details
Source Beth Israel Deaconess Medical Center (Boston, MA)
Data Provider PhysioNet - MIT Lab for Computational Physiology
Time Period 2008-2019
Total ICU Admissions ~76,000 admissions
Curated Dataset Size ~30,000-40,000 admissions (after filtering)
Access Requires CITI training and PhysioNet credentialing

CSV Files Used in This Project

  • patients.csv - Patient demographics (age, gender)
  • admissions.csv - Hospital admission details (admission type, admission time)
  • icustays.csv - ICU stay information (ICU admission/discharge times)
  • diagnoses_icd.csv - ICD diagnosis codes for identifying comorbidities
  • prescriptions.csv - Medication prescriptions (antibiotic history)
  • labevents.csv - Laboratory test results (WBC, creatinine, lactate, etc.)
  • chartevents.csv - Vital signs and clinical observations (HR, BP, temperature, SpO2)
  • microbiologyevents.csv - Microbiology culture results (used for labeling only)
Data Preprocessing: The raw MIMIC-IV dataset was filtered to include only ICU admissions with sufficient data and available microbiology results for labeling. Admissions with incomplete records or missing critical features were excluded to ensure data quality.

Feature Engineering

All features are derived exclusively from data available within the initial hours of ICU admission to ensure the model provides early risk prediction before traditional culture results are available.

⚠ Temporal Constraint: Features must be available within 24 hours to ensure practical clinical utility. Any data recorded after the 24-hour mark is excluded to prevent data leakage.

Feature Processing Steps

  1. Time Filtering: Extract only records within first 24 hours of ICU admission
  2. Aggregation: Calculate mean, median, min, max for vital signs and lab values
  3. Missing Value Handling: Use median imputation for continuous variables, mode for categorical variables
  4. Encoding: One-hot encoding for categorical features (gender, admission type)
  5. Normalization: Standardize continuous features (z-score normalization)

Labeling Methodology

The target variable (AMR presence) is derived from microbiology culture results recorded in microbiologyevents.csv.

Labeling Strategy

Positive Label (AMR = 1)

Patient has at least one culture result with resistant (R) susceptibility status for any antibiotic tested within 7 days of ICU admission.

Negative Label (AMR = 0)

Patient has culture results showing susceptible (S) status for all antibiotics tested, or no resistant organisms detected within 7 days of ICU admission.

Patient-Level Labeling

Since patients may have multiple cultures, we use a patient-level aggregation approach:

  • If any culture shows resistance → Label = 1 (AMR positive)
  • If all cultures show susceptibility → Label = 0 (AMR negative)
  • Patients with inconclusive or intermediate results are excluded from training
⚠ Critical: Preventing Data Leakage
Microbiology data is used ONLY for labeling, never as an input feature. The model cannot access culture results, organism types, or susceptibility patterns during prediction. This ensures the model learns to predict AMR risk from early clinical indicators alone, mimicking real-world scenarios where culture results are not yet available.

Data Distribution

Label Count Percentage
AMR Negative (0) ~24,000 ~68%
AMR Positive (1) ~11,000 ~32%
Total ~35,000 100%

The dataset exhibits class imbalance (more negative cases than positive), which is handled through:

  • Class weighting: Assign higher weights to positive (AMR) cases during training
  • Evaluation focus: Prioritize recall/sensitivity to minimize false negatives
  • Stratified sampling: Ensure balanced representation in train/test splits

Machine Learning Approach

Model Selection

We employ a XGBoost classifier (ensemble learning method) for the following reasons:

  • Robustness: Handles non-linear relationships and feature interactions effectively
  • Interpretability: Provides feature importance scores for clinical transparency
  • Performance: Strong predictive performance on tabular healthcare data
  • Low overfitting: Ensemble approach reduces variance

Training Strategy

We use a temporal train-test split to simulate real-world deployment:

  • Training Set: ICU admissions from 2008-2017 (~70%)
  • Test Set: ICU admissions from 2018-2019 (~30%)
  • Rationale: Temporal split prevents data leakage and tests model generalization to future time periods
Cross-Validation: 5-fold stratified cross-validation is performed on the training set for hyperparameter tuning and model selection.
